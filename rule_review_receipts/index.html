    Receipts for rule reviews

    A rule review ends in a verdict on somebody else's annotation rule. The verdict is only as good as the facts behind it, so every claim in a review must come with a receipt: a fact, in a field a program can test, that names its source. The idea is from Show me the receipts: do not ask the reviewer for a verdict, ask for a verdict plus the receipts, and check the receipts.

    This page says what counts as a receipt in a rule review, which checks run, and why. It exists because an audit of the 78 ARBA reviews in November 2026 found that about 45 of them reached a verdict their own evidence did not support. Nearly all of the errors were detectable from the file.

    The "limit of 12 condition sets" is max_condition_sets=12 in src/ai_gene_review/etl/rule_analysis.py, the number of sets the overlap analysis reads by default. It says nothing about whether a rule is right.

    What a receipt is

    Claim Receipt
    "The rule has these conditions" rule.condition_sets copied from the fetched rule, with rule.retrieved_date and rule.source_condition_set_count
    "IPR000999 is X" the official InterPro name as the condition's label; in prose, IPR000999 (Ribonuclease III domain)
    "GO:nnnnnnn means X" / "is more specific than Y" the GO label, and the parent that makes it a descendant
    "This protein is wrongly annotated" a UniProt accession in annotation_assessments[].incorrect_examples, and no experimental annotation to the term or a descendant
    "This set is right" accessions in correct_examples, each with the GO id, evidence code and reference in notes
    "N proteins match" the UniProtKB query, the count and the release
    "The literature says" a PMID or DOI, and a supporting_text that is verbatim in the cached paper

    A note the reviewer wrote, an AI deep-research file, and a file that does not exist are not receipts. Notes and research files are where leads come from; the receipt is the paper or database record the lead points to.

    Rules for verdicts

    • UNDECIDED is the verdict for a rule that was not examined. A rule with hundreds of condition sets that nobody read set by set is UNDECIDED, however general its term. Say which sets were sampled and what they showed.
    • ACCEPT covers the whole rule. Every condition set served at retrieved_date is recorded and supported.
    • MODIFY and SPLIT name the change. A specific set, protein or term, in suggested_modifications.
    • DEPRECATE needs a wrongly annotated protein, an obsolete consequent or a withdrawn rule. A true but general term, a redundant rule and a rule with low recall are not wrong.
    • Read condition sets as conjunctions. A set is the proteins that match all its conditions, including the taxon. Judge that set, never one of its signatures. Alternative sets are expected to be disjoint.
    • A FunFam label is the name of one member, not the identity of every member. Check what the conjunction matches in UniProtKB.
    • Check the alleged false positive before writing it down. Look up the protein's experimental annotations to the term and its descendants. The rule was mined from such annotations, so a surprising family is more often a curated annotation the reviewer did not know than an error.
    • confidence is confidence in the verdict. Below 0.5, the verdict is UNDECIDED.
    • A wrong claim is withdrawn in corrections, with the evidence that refuted it, and removed from the prose.

    The checks

    just rules-validate runs the schema check and then src/ai_gene_review/validation/rule_review_receipts.py. Errors fail the file.

    Check Severity Fires when
    verdict_without_conditions error action is not UNDECIDED and rule.condition_sets is empty
    missing_rule_snapshot error (warning when UNDECIDED) no rule.retrieved_date, or a verdict with no rule.source_condition_set_count on a rule that is not withdrawn
    verdict_without_confidence error action is not UNDECIDED and no confidence is stated
    accept_on_partial_examination error ACCEPT with fewer sets recorded than source_condition_set_count
    condition_label_mismatch, go_label_mismatch error a recorded label differs from the official one in rules/_labels.json
    prose_identifier_label_mismatch error / warning prose writes ID (name) or name (ID) and the name shares no word with the official label
    condition_set_out_of_range error prose or a reference finding names a condition set number higher than the rule as recorded has (usually text left over from an earlier version of the rule)
    size_as_evidence error a review that faults the rule (DEPRECATE, MODIFY, SPLIT, MERGE) appeals to a limit, threshold or recommended maximum of condition sets
    unresolvable_reference error supported_by cites something that is not a PMID, DOI, database record, URL or file
    missing_cited_file error a cited file: does not exist
    own_notes_as_support warning supported_by cites notes or an AI research file
    literature_verdict_without_literature error literature_support is STRONG, MODERATE or CONTRADICTED and the block itself (its supported_by or notes) names no publication or curated pathway record
    deprecate_without_counterexample error DEPRECATE with no incorrect_examples, no consequent_obsolete: true and no withdrawn rule
    modify_without_modification error MODIFY, SPLIT or MERGE with no suggested_modifications
    low_confidence_verdict error a verdict other than UNDECIDED at confidence below 0.5
    example_not_an_accession error an example is not a UniProt accession

    just rules-validate --online <file> adds two checks that need the network:

    Check Severity Fires when
    false_positive_has_experimental_annotation error an incorrect_examples accession carries the consequent, or a descendant, on experimental evidence in QuickGO
    stale_rule_snapshot, rule_withdrawn_upstream warning UniProt now serves a different number of condition sets, or no longer serves the rule
    withdrawn_but_served error rule.withdrawn is true but UniProt serves the rule
    consequent_not_obsolete error consequent_obsolete is true but QuickGO serves the term as current
    online_check_failed warning a lookup failed, so that check did not run; a clean --online result with this warning is not a pass

    Run --online before marking a review COMPLETE.

    A receipt field left out is not a pass. The checks that test a field also require it: a verdict must state its rule snapshot and its confidence, and the two grounds that excuse a DEPRECATE from naming a protein (withdrawn, consequent_obsolete) are both verified online. FunFam labels are compared with the cache but cannot be refreshed by --refresh-labels, which covers InterPro and GO only; update a renamed FunFam label in rules/_labels.json by hand, from CATH.

    The label checks compare against the committed cache rules/_labels.json. InterPro renames entries, so a label error can mean the cache is stale. Run uv run python -m ai_gene_review.validation.rule_review_receipts --refresh-labels <file>: it re-fetches only the identifiers whose recorded label disagrees with the cache. If the error remains, the review is wrong.

    What ACCEPT means

    In the corrected reviews, ACCEPT means every condition set was examined and its reviewed (Swiss-Prot) matches carry the consequent on evidence other than ARBA itself, usually with an experimental annotation in each set. Swiss-Prot entries can carry a term only as an ARBA IEA (GO_REF:0000117); those are the rule's own output and are excluded. This is still in-sample evidence: the rule was mined from Swiss-Prot, and the unreviewed entries it annotates were counted, not inspected. Read ACCEPT as "no conflict found", and keep the confidence modest.

    What the checks cannot see

    Deterministic checks test that a receipt exists and resolves. They do not test that it supports the claim it is attached to. A real PMID can be cited for something the paper does not say, and a real accession can be a poor example. Two things cover that gap:

    • Spot-checks by a second reader. The November 2026 audit was this: independent readers re-derived the facts each verdict depended on. Sample new reviews the same way, starting with DEPRECATE verdicts and anything a reviewer flags as unusual.
    • Corrections as test cases. Each corrections entry records a claim, its error_type and the refuting evidence. Count them by error_type to see which errors recur, and turn recurring ones into a check here or a line in the reviewer skill.

    Receipts can also be written after the fact to fit a verdict. That is why the online check looks for evidence against the review (experimental annotation on an alleged false positive) and not only for evidence the reviewer chose to cite.
