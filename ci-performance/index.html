    CI validation performance

    Measurements (2026-10-11)

    The successful DANRE audit run spent 28m55s executing, after roughly four hours queued. Its major steps were:

    Step Time
    Family validation 21m36s
    Disk cleanup 2m01s
    Changed gene validation 1m50s
    Checkout 1m49s
    History validation and tests 55s
    Dependency installation 9s

    The CNOT1 run showed the same pattern: family validation took 21m30s, while changed gene validation took 21s. The ontology cache restored in 14s and PANTHER cache in 5s. Downloads and dependency installation were not the dominant cost in these runs.

    Every gene-review edit triggers the family checks because gene residue claims and family assessments must agree. That coverage is intentional. Within the DANRE run's family step, the schema phase took 6m21s and the term phase 14m36s: each started a new validator process for each of 281 family reviews. Reference validation was already batched; residue checks and cross-checks together took about 20s.

    Changes

    Following dismech's validate-disorders recipe, validate-families now runs one schema invocation and one term invocation over all family files. validate-modules likewise batches its schema phase. Schema generation, Python imports, and ontology initialization can be reused within each process. All existing files, validation phases, and blocking exit statuses are retained. Quoted Bash arrays preserve filenames containing spaces.

    One diagnostic tradeoff: an uncaught loader or validator exception can stop a batch before later files are checked. The phase still exits nonzero and blocks CI, and subsequent validation phases still run, but errors in later files may only appear after the malformed file is fixed and validation is rerun.

    As in dismech's CI workflow, the unconditional disk cleanup is replaced with a capacity report. Our sampled runner already had 86 GB free before spending two minutes deleting SDKs and Docker images. Revisit this if runner capacity or repository size changes.

    Local checks on this checkout passed for all 283 family reviews (14.54s schema, 42.77s terms) and all 450 module schemas (12.33s). These are local timings, not post-change GitHub runner measurements. Regression tests exercise failures in each recipe phase and verify that the real schema and term validators reject an invalid second file after a valid first file. Absolute times vary with cache state and machine load; use the same-machine comparison below to isolate the benefit of batching.

    A same-machine comparison on the first ten sorted family reviews isolates the batching effect (both modes passed with the same schema, flags, and inputs):

    Phase One process per file One batch
    Schema 9.73s 0.85s
    Terms 20.32s 2.11s

    Merge-queue follow-up (2026-10-12)

    After the first speedup, the successful merge-group run 38180881453 spent about 40 minutes executing. Family validation fell to 62 seconds. The remaining large steps were all-gene schema validation (454 seconds), module validation (706 seconds), and the test suite including doctests and mypy (834 seconds). Checkout took 117 seconds and fetching frozen benchmark snapshots 57 seconds. A second successful integration run showed similar timings.

    The follow-up removes repeated work within those steps:

    • Gene schema batches use libyaml's safe parser with LinkML's existing closed JSON Schema plugin. Instance boundaries, diagnostics, and blocking errors are retained; duplicate-key checking remains in the existing strict-YAML tests. The C scanner can differ on malformed/edge-case input (for example, trailing tabs and lone Unicode surrogates); it is not a byte-for-byte parser replacement. Installations without libyaml fall back to PyYAML's safe Python parser.
    • Module ontology labels and aliases are shared across files within one CLI invocation, keyed by ontology adapter and term. Lookup exceptions are remembered within a file to avoid repeated timeouts, then retried on the next file. Nothing is persisted across runs or skips document validation.
    • Reaction-chaining QC resolves reactions only for steps participating in a PRECEDES connection. Unconnected steps cannot contribute to these findings; their other structural and functional checks still run.
    • Git snapshot glob searches use a sorted path index to narrow candidates by literal prefix before applying the unchanged matcher. Results are cached only within the immutable snapshot; callers receive independent result lists.
    • The ProtNLM and BioReason benchmark readers use the same safe parser. Frozen inputs, ontology releases, expected scores, and test coverage are unchanged.

    Same-machine measurements on the same checkout (Python 3.12, warm ontology caches) show:

    Check Before After
    All 6,711 checked-out gene schemas 251.48s 62.86s
    First 100 sorted gene schemas 2.96s 1.29s
    First 50 sorted module files, grounding/QC phase 128.15s 82.53s
    ProtNLM + BioReason benchmark tests (26 tests) 146.03s 42.88s

    The module comparison produced byte-identical diagnostics. All 448 module files passed the new grounding/QC batch (412.83s). Benchmark timings use pytest reported duration; the baseline restores both the original glob and YAML loaders in a separate process. Both versions pass the same 26 tests against frozen inputs. These are local measurements with other checks running concurrently, not promised GitHub runner timings. Both full schema runs passed. The additional DROME/Dl review hidden by this macOS checkout's Dl/dl filename collision was exported from Git and validated separately. Integration runs must establish the end-to-end improvement after merge.

    Remaining opportunities

    • Queue pressure is distinct from execution time. The separate superseded-run cancellation PR #4883 addresses obsolete PR runs holding runners. Faster validation should also reduce queue occupancy.
    • Changed gene validation still runs the external validators per gene through the CLI. Batching those phases would help large curation PRs, but must retain per-file diagnostics, reference preprocessing, and gene-specific checks.
    • Infrastructure changes intentionally trigger full-corpus validation; ordinary review PR timings do not predict that cost.
    • Checkout and repo-wide history checks remain measurable costs. Reassess them after observing the batched family phase in CI.

    Dismech additionally uses cache-bound reference checks, offline term checks in selected CI lanes, and cached generated JSON Schema for single-file validation. Those policies were not copied here: the measured family bottleneck can be removed without changing reference fetching or ontology freshness behavior.

    To reproduce the family phase timings, run these separately under time:

    uv run linkml-validate --schema src/ai_gene_review/schema/family_review.yaml \
  --target-class FamilyReview interpro/panther/PTHR*/PTHR*-review.yaml
uv run linkml-term-validator validate-data interpro/panther/PTHR*/PTHR*-review.yaml \
  -s src/ai_gene_review/schema/family_review.yaml -t FamilyReview \
  --labels -c conf/oak_config.yaml

    For end-to-end timing, use time just validate-families with warm PANTHER and UniProt caches, as in the sampled CI runs. Cold-cache network time is a separate measurement.
